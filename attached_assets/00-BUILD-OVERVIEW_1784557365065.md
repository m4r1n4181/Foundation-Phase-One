## What this product is

A **pre-visit preparation and clinical-context tool** for a thyroid
endocrinology clinic. It is explicitly **not** an EMR and does not store the
official medical record. Patients fill a short structured questionnaire and
declare/upload lab status before their appointment; the doctor gets a
read-only dashboard with deterministic (non-AI) templated summaries and a
longitudinal history. Clinic admin/reception staff get an operational view
only, with no access to clinical content.

Core hypothesis being tested: structured pre-visit intake + templated
summaries → shorter, more focused consultations, less repetitive questioning,
less doctor documentation burden — without compromising clinical quality.

## Explicitly OUT of scope for MVP — do not build these

- Any LLM-generated content (summaries are 100% deterministic/template-based)
- Full OCR lab extraction / lab normalization / anomaly detection / clinical interpretation (only lightweight advisory date-extraction is in scope, see below)
- Doctor-facing PDF as the primary interface
- CSV roster ingestion / scheduling-system integration
- Doctor editing of patient-entered data
- Persistent patient portal after appointment completion
- Blocking questionnaire submission because labs are missing (warn, never block)
- Summary versioning (only the latest generated summary is shown)
- EMR replacement functionality of any kind

If a request during later iteration seems to require any of the above, stop
and flag it rather than implementing it — these were explicitly removed by
the product owner after review.

## Tech stack (carry over from prior architecture decisions)

- **Backend:** Node.js, Fastify, API-first modular monolith (not microservices for MVP)
- **Database:** PostgreSQL
- **Background jobs / reminders:** BullMQ
- **Auth:** Auth.js (or equivalent), extended with the patient-side magic-link + DOB + SMS OTP flow described in `02-DATA-MODEL-ROLES-AUTH.md` — this patient flow is custom, it is not the same as staff/doctor login
- **Hosting:** AWS (data residency/region is a pending legal decision — see `04-COMPLIANCE-CONSTRAINTS.md`; build with region as a configuration value, not a hardcoded assumption)
- **Frontend:** mobile-first responsive web app for patients; mobile+desktop responsive dashboard for doctors and admin/reception. No native app in MVP.
- **File storage:** encrypted object storage (e.g. S3 with server-side encryption) for uploaded lab/ultrasound documents

## Roles (see 02 for full RBAC matrix)

`patient`, `doctor`, `clinic_admin` (reception/admin/staff), and a
configurable `nurse` role slot — the legal doc and PRD both flag "is a nurse
role needed beyond doctor and admin?" as unresolved. Build the role system so
a `nurse` role can be added later without a schema change (i.e. permissions
are role-based, not hardcoded to "doctor OR admin").

## Suggested build order

1. Data model + auth (patient magic-link+DOB flow; doctor/admin login) — see `02-DATA-MODEL-ROLES-AUTH.md`
2. Clinic admin console: create/resend/edit/cancel appointment invitations
3. Patient flow: identity verification → questionnaire → uploads/lab status → save/submit/lock
4. Deterministic summary generation engine (template-based, config-driven per `03`)
5. Doctor dashboard: daily list → patient detail → summaries → historical timeline
6. Reminder engine (BullMQ jobs tied to appointment timing + completion status)
7. Audit logging (should really be threaded through from step 1, not bolted on at the end)
8. Stage 0 usability test support (no special code needed beyond the above being functional end-to-end)

## Non-negotiable cross-cutting requirements

- Every access to patient clinical data (by any role) is audit-logged. This is not optional and not deferrable to "later."
- All patient data is encrypted at rest and in transit.
- Admin/reception role can never see questionnaire answers or documents — this must be enforced at the API/authorization layer, not just hidden in the UI.
- Questionnaire data is patient-reported, not verified clinical truth — this should be reflected in copy, not just internal docs.
- The platform must say clearly, in the product itself, that it is not the official medical record.
